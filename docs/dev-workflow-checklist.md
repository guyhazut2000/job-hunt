# שיטת העבודה בפיתוח: צ'קליסט מעמיק

> מסמך עבודה שאפשר לחזור אליו בכל פיצ'ר, תיקון באג או שדרוג ספרייה.
> הדוגמאות לקוחות מהפרויקט הזה (Next.js 15, TypeScript, Prisma, Neon, Vercel, GitHub Actions), אבל השלבים
> עצמם מתאימים לכל פרויקט. דוגמה מלאה שעוברת על כל השלבים בפיצ'ר אמיתי:
> [dev-workflow-example.md](dev-workflow-example.md).

## העיקרון המרכזי

**עובדים בצעדים קטנים, ולא מכריזים "גמור" לפני שראינו שזה עובד באתר החי.**

כל השלבים למטה הם דרכים לקיים את המשפט הזה: להגדיר מראש מה זה "עובד", לשנות מעט בכל פעם, לבדוק
אוטומטית וגם ידנית, ולוודא בסוף שהמשתמש האמיתי מקבל את מה שהבטחנו.

## שלב 1: להבין מה באמת צריך ולהגדיר הצלחה

**למה זה חשוב:** בקשה כמו "לשפר את החיפוש" אפשר לממש בעשר דרכים, ורק אחת מהן היא מה שהתכוונו אליו.
אם לא מגדירים מראש איך נראית הצלחה, אי אפשר לדעת מתי לעצור, ואי אפשר להוכיח שזה עובד. הגדרה טובה
הופכת אחר כך ישירות לבדיקה אוטומטית ולצ'קליסט של הבדיקה הידנית.

- [ ] לנסח את הבעיה במשפט אחד מנקודת המבט של המשתמש ("כשאני מוחק מועמדות בטעות, אין דרך להחזיר אותה").
- [ ] לכתוב 2–5 **קריטריוני הצלחה שאפשר לבדוק**, בצורה "כאשר X, אז Y". למשל: "חיפוש `אינטל` מחזיר את
      אותן חברות כמו `Intel`".
- [ ] לכתוב מה **לא** נכלל בעבודה (non-goals), כדי שהיקף העבודה לא יתפח.
- [ ] לזהות אילוצים: אבטחה, פרטיות, תנאי שימוש של אתרים אחרים, מכסות חינמיות, ביצועים, נגישות, RTL.
- [ ] לזהות החלטות מוצר פתוחות (למשל "טען עוד" מול חלוקה לעמודים). אם יש כאלה, לשאול את בעל המוצר
      **לפני** שכותבים קוד, ולהציג 2–3 אפשרויות עם יתרונות וחסרונות.
- [ ] לפתוח issue (או לעדכן קיים) עם הניסוח והקריטריונים.

```bash
gh issue create --title "Undo for deleting an application" \
  --body $'Problem: ...\n\nSuccess criteria:\n- [ ] ...\n\nOut of scope:\n- ...'
gh issue list --search "undo in:title" --state all   # אולי כבר יש issue
```

**טעויות נפוצות**

- להתחיל לכתוב קוד מתוך "ברור לי מה צריך".
- קריטריון שאי אפשר למדוד ("יותר מהיר", "יותר נוח") במקום מספר או התנהגות ("העמוד שוקל פחות מ-500KB").
- להחליט לבד על משהו שהוא בעצם החלטת מוצר.

**הגדרת "סיום":** יש ניסוח בעיה, קריטריונים שאפשר לבדוק, רשימת non-goals, ואין החלטות מוצר פתוחות.

## שלב 2: לקרוא את הקוד לפני שכותבים

**למה זה חשוב:** קוד חדש צריך להיראות כמו הקוד הקיים. מי שמכיר את הדפוסים בפרויקט (איך שומרים נתונים,
איך כתובות הבדיקות, איך מתרגמים טקסטים) לא ממציא מחדש דברים שכבר קיימים, ולא שובר הנחות שחלקים
אחרים בקוד נשענים עליהן.

- [ ] למצוא את נקודת הכניסה של הפיצ'ר: העמוד, הקומפוננטה, ה-server action או ה-API route.
- [ ] לעקוב אחרי הנתונים מקצה לקצה: UI ← action/route ← `db` (Prisma) ← סכמה.
- [ ] לבדוק את הסכמה (`prisma/schema.prisma`): קשרים, `onDelete: Cascade`, אינדקסים ו-`@@unique`
      שעלולים להתנגש בפתרון.
- [ ] לחפש קוד דומה שכבר קיים ולהעתיק את הדפוס שלו (למשל איך עוד מקום בקוד מציג toast או undo).
- [ ] לקרוא את הבדיקות הקיימות באזור, ואת המסמך הרלוונטי ב-`docs/`.
- [ ] לבדוק את ההיסטוריה: מי שינה את הקובץ לאחרונה ולמה.
- [ ] לרשום לעצמך 3–5 עובדות שגילית שמשפיעות על התכנון.

```bash
rg -n "removeApplication" src            # מי קורא לפונקציה
rg -n "model Application" -A 40 prisma/schema.prisma
git log --oneline -10 -- src/components/Kanban.tsx
git log -S "useOptimistic" --oneline     # מתי נכנס דפוס מסוים
ls tests | rg -i "kanban|application"
```

**טעויות נפוצות**

- לקרוא רק את הקובץ שעומדים לשנות, ולפספס עשרות מקומות אחרים שמושפעים (למשל כל השאילתות על טבלה).
- להוסיף ספרייה חדשה כשבפרויקט כבר יש כלי שעושה את אותו הדבר.

**הגדרת "סיום":** אפשר להסביר במשפט איפה השינוי יקרה, מה הוא עלול לשבור, ואיזה דפוס קיים הוא ממשיך.

## שלב 3: לפרק ל-PRs קטנים שמקושרים ל-issue

**למה זה חשוב:** PR קטן עם מטרה אחת אפשר לסקור בכמה דקות, קל להבין ממנו מה השתנה, ואם הוא שובר
משהו קל להחזיר אותו אחורה (`git revert`) בלי לאבד עבודה אחרת. PR ענק מסתיר באגים ומעכב את כולם.

- [ ] לכתוב תוכנית קצרה: רשימת שינויים לפי סדר, ומה תלוי במה.
- [ ] כל PR עושה **דבר אחד** שאפשר לתאר בשורה אחת. אם צריך "וגם" בכותרת, כנראה שאלה שני PRs.
- [ ] יעד גודל: עד כמה מאות שורות של שינוי אמיתי (בלי קבצים שנוצרו אוטומטית).
- [ ] כשיש תלות: PR של תשתית או סכמה קודם, PR של UI אחריו. לרשום את הסדר ב-PR עצמו.
- [ ] לקשר ל-issue: `Closes #N` כש-PR מממש את כל ה-issue, ו-`Refs #N` כשהוא רק חלק ממנו.
- [ ] כותרת בסגנון Conventional Commits: `feat(dashboard): ...`, `fix(auth): ...`, `chore(deps): ...`, `docs: ...`.

**טעויות נפוצות**

- לערבב ריפקטור, פיצ'ר ושדרוג ספרייה באותו PR.
- לכתוב `Closes` על issue שרק חלק ממנו מומש. ה-issue ייסגר אוטומטית והחלק שנשאר יישכח.

**הגדרת "סיום":** לכל PR יש מטרה אחת, כותרת ברורה, קישור ל-issue וסדר מיזוג ידוע.

## שלב 4: ענף ותיקייה נפרדים לכל עבודה

**למה זה חשוב:** `master` צריך להיות תמיד במצב שאפשר להעלות לאתר. עבודה בענף נפרד מבודדת את השינוי.
`git worktree` נותן לכל ענף תיקייה משלו, כך שאפשר לעבוד על שני פיצ'רים במקביל, או לתקן באג דחוף, בלי
`stash` ובלי לערבב קבצים.

- [ ] לעדכן את `master` לפני שמתחילים.
- [ ] לפתוח ענף עם שם תיאורי: `feat/<נושא>`, `fix/<נושא>`, `chore/deps-<ספרייה>`, `docs/<נושא>`.
- [ ] לפתוח worktree לענף בתיקייה נפרדת, ולהתקין בה תלויות.
- [ ] לא לעבוד ישירות על `master`, ולא לעשות `push --force` לענף שמישהו אחר עובד עליו.
- [ ] בסיום: למחוק את ה-worktree ואת הענף המקומי.

```bash
git fetch origin
git worktree add -b feat/delete-undo ../job-hunt-delete-undo origin/master
cd ../job-hunt-delete-undo && npm ci
# ... עבודה ...
git push -u origin feat/delete-undo
# אחרי המיזוג:
git worktree remove ../job-hunt-delete-undo && git branch -D feat/delete-undo
git worktree prune
```

**טעויות נפוצות**

- ענף ישן שלא עודכן מ-`master`, ואז קונפליקטים גדולים בסוף. עדיף `git rebase origin/master` מוקדם ולעתים קרובות.
- worktrees ושרתי פיתוח שנשכחים פתוחים וצורכים זיכרון ומעבד (ראו שלב 10).

**הגדרת "סיום":** העבודה נמצאת בענף משלה, בתיקייה משלה, ו-`master` לא נגעו בו.

## שלב 5: שינויים בטוחים במסד הנתונים

**למה זה חשוב:** מסד הנתונים הוא הדבר היחיד שאי אפשר "לפרוס מחדש". קוד אפשר להחזיר בלחיצה, נתונים
שנמחקו לא חוזרים. בפרויקט הזה גם סביבות ה-preview משתמשות במסד של production, ולכן migration רצה על
נתונים אמיתיים כבר בזמן ה-PR. גם rollback מיידי ב-Vercel לא מבטל migration.

- [ ] קודם לשאול: **האם צריך בכלל שינוי סכמה?** לפעמים פתרון בצד הקוד חוסך migration (ראו הדוגמה).
- [ ] migrations **מוסיפות בלבד**: טבלה חדשה, עמודה nullable או עם default, אינדקס. בלי `DROP`, בלי
      `RENAME`, ובלי `NOT NULL` על עמודה קיימת בלי default.
- [ ] מחיקה או שינוי שם נעשים בשלבים, ב-PRs נפרדים: (1) להוסיף את החדש, (2) לכתוב לשניהם ולהעביר נתונים,
      (3) לקרוא רק מהחדש, (4) רק אחר כך, ב-PR נפרד ועם אישור, להסיר את הישן.
- [ ] לפני שינוי נתונים (backfill, עדכון המוני): גיבוי שממנו אפשר לשחזר. ב-Neon זה branch מהמצב הנוכחי.
- [ ] לייצר את ה-migration עם `--create-only`, ולקרוא את ה-SQL לפני שמריצים אותו.
- [ ] להריץ את בדיקת ה-additive המקומית.
- [ ] כל שאילתה חדשה מסננת לפי המשתמש (`where: { userId }`), כדי שמשתמש אחד לא יגיע לנתונים של אחר.

```bash
npx prisma migrate dev --create-only --name add_application_followup_at
cat prisma/migrations/*_add_application_followup_at/migration.sql   # לקרוא את ה-SQL!
npx prisma migrate dev            # להחיל מקומית
npm run db:check-additive         # אותה בדיקה ש-CI מריץ
# גיבוי לפני backfill: ב-Neon ליצור branch (Console / neonctl / MCP), למשל:
neonctl branches create --name backup-before-backfill-2026-10-31
```

**טעויות נפוצות**

- שינוי ב-`schema.prisma` בלי migration. ב-CI יש בדיקת drift שתיכשל.
- להניח שאפשר "לתקן אחר כך" migration שכבר רצה על production.
- backfill בלי גיבוי, או בלי לבדוק קודם על כמה שורות הוא ישפיע (`SELECT count(*)`).

**הגדרת "סיום":** אין שינוי סכמה, או שיש migration מוסיפה בלבד שה-SQL שלה נקרא, הבדיקה עוברת, ולפני כל שינוי נתונים יש גיבוי.

## שלב 6: בדיקות כחלק מהפיצ'ר

**למה זה חשוב:** בדיקה היא ההוכחה שהקריטריונים משלב 1 מתקיימים, והיא ממשיכה להוכיח את זה גם אחרי
שינויים עתידיים. בפרויקט יש גם בדיקות "שמירה" (guards) שתופסות מצב שבו חלקים בפרויקט כבר לא מתאימים
זה לזה. למשל `tests/features-registry.test.ts` מכשילה את ה-CI אם נוסף עמוד שלא מופיע בדף הפיצ'רים.

- [ ] לכל קריטריון הצלחה, לפחות בדיקה אחת.
- [ ] בדיקות למקרה הרגיל **ולמקרי קצה**: קלט ריק, כפול, לא תקין, גבולות (0, 1, המקסימום), כשל רשת, משתמש לא מחובר.
- [ ] להפריד לוגיקה טהורה מה-UI (פונקציה או מודול ב-`src/lib/`) כדי שאפשר לבדוק אותה מהר ב-vitest, בלי דפדפן.
- [ ] להזריק תלויות כמו טיימרים, זמן ורשת, כדי שהבדיקות יהיו דטרמיניסטיות ולא "פלאקיות".
- [ ] כל באג שנמצא הופך לבדיקת רגרסיה **לפני** התיקון: קודם רואים אותה נכשלת, ואז מתקנים.
- [ ] כשיש כלל שצריך להישמר בכל הפרויקט, לשקול בדיקת guard במקום להסתמך על זיכרון.
- [ ] שירותים חיצוניים (Gemini, Gmail) רצים בבדיקות במצב mock. בדיקה לא קוראת ל-API אמיתי.

```bash
npx vitest run tests/delete-undo.test.ts   # רק הקובץ שעובדים עליו
npm test                                   # הכל, כמו ב-CI
npm run lint && npm run format:check && npm run typecheck
npm run build                              # לתפוס שגיאות שמופיעות רק ב-build
```

**טעויות נפוצות**

- בדיקות שבודקות את המימוש (קריאות פנימיות) במקום את ההתנהגות.
- `setTimeout` אמיתי בבדיקה, ובדיקה שלוקחת 7 שניות ונכשלת לפעמים.
- "אוסיף בדיקות ב-PR הבא". זה כמעט אף פעם לא קורה.

**הגדרת "סיום":** כל קריטריון מכוסה בבדיקה, יש בדיקות למקרי קצה, ו-lint, format, typecheck, test ו-build עוברים מקומית.

## שלב 7: לבדוק כמו משתמש ולמדוד

**למה זה חשוב:** בדיקות אוטומטיות לא רואות שכפתור מוסתר מאחורי סרגל הניווט במובייל, שטקסט עברי נשבר
לא נכון, או שהעמוד שוקל 5MB. "עובר אצלי" ו"הבדיקות ירוקות" עוד לא אומרים שהמשתמש מרוצה.

- [ ] להריץ build של production מקומית (`next start`), לא רק `next dev`, כי ההתנהגות שונה.
- [ ] לעבור על כל קריטריון הצלחה ידנית, או עם סקריפט Playwright, **במובייל (390px) ובמחשב**.
- [ ] לצלם מסך לפני ואחרי, במובייל ובמחשב, ולשמור את הצילומים מחוץ לריפו.
- [ ] לבדוק RTL: כיוון טקסט, אייקונים, אנימציות (`origin-left` לעומת `rtl:origin-right`), טקסט מעורב עברית ואנגלית (`dir="auto"`).
- [ ] נגישות: ניווט במקלדת, פוקוס, `aria-label`, `role="status"` להודעות, יעד לחיצה בגודל 44px לפחות.
- [ ] לבדוק שאין שגיאות ב-console.
- [ ] **למדוד** את מה שהבטחנו: גודל העמוד, זמן טעינה, מספר שאילתות, ולהשוות לפני ואחרי.
- [ ] לנסות מקרים "רעים": רענון באמצע, ניווט החוצה באמצע פעולה, שני טאבים, רשת איטית.

```bash
npm run build && npx next start -p 3100 &      # לזכור את ה-PID ולסגור בסוף
# צילומי מסך במובייל ובמחשב (Playwright):
npx playwright screenshot --viewport-size=390,844 http://localhost:3100/companies shots/mobile-before.png
npx playwright screenshot --viewport-size=1440,900 http://localhost:3100/companies shots/desktop-before.png
# מדידת גודל HTML:
curl -s -o /dev/null -w "%{size_download} bytes, %{time_total}s\n" http://localhost:3100/companies
```

**טעויות נפוצות**

- לבדוק רק במחשב ורק כשהמשתמש מחובר, או רק כשהוא לא מחובר.
- להסתפק ב"נראה מהר יותר" בלי מספר.
- להשאיר שרת `next dev` פתוח ברקע. הוא ממשיך לצרוך משאבים.

**הגדרת "סיום":** כל קריטריון נבדק ידנית במובייל ובמחשב, יש צילומי מסך ומדידה לפני ואחרי, ואין שגיאות ב-console.

## שלב 8: CI ירוק, מיזוג לפי סדר, ובדיקה באתר החי

**למה זה חשוב:** ה-CI הוא שומר הסף האובייקטיבי. הוא מריץ את אותן בדיקות על סביבה נקייה. אבל גם CI ירוק
לא מבטיח שהגרסה עלתה, שה-migration רצה, או שהעמוד עובד עם הנתונים האמיתיים. לכן העבודה נגמרת רק
אחרי בדיקה באתר החי.

- [ ] לפתוח PR לפי התבנית (למטה), עם `Closes #N` או `Refs #N`.
- [ ] לחכות שכל ה-checks יהיו ירוקים. ב-CI של הפרויקט: lint, format, typecheck, tests, migrate deploy,
      drift, additive migrations, seed, build.
- [ ] אם CI נכשל: לקרוא את הלוג, להבין את הסיבה, לתקן ב-commit נוסף. לא לעקוף ולא לנטרל בדיקה.
- [ ] לעבור על ה-diff הסופי בעצמך, כאילו אתה הסוקר.
- [ ] למזג לפי סדר התלות (תשתית לפני UI). אחרי כל מיזוג, לחכות שה-deploy יעלה לפני המיזוג הבא.
- [ ] לוודא שה-deploy ב-Vercel במצב `READY` ושהוא מה-commit הנכון.
- [ ] לפתוח את האתר החי ולעבור שוב על הקריטריונים העיקריים (smoke test), במובייל ובמחשב.
- [ ] אם משהו שבור ב-production: rollback מיידי ב-Vercel (לקוד בלבד), ואז תיקון ב-PR חדש.

```bash
gh pr create --base master --head feat/delete-undo \
  --title "feat(dashboard): undo for deleting an application" \
  --body-file pr-body.md               # כולל "Closes #N" או "Refs #N"
gh pr checks --watch                   # לחכות לתוצאה
gh run view --log-failed               # אם נכשל: רק השלבים שנכשלו
gh pr merge --squash --delete-branch
# לוודא שה-deploy עלה (ה-token נקרא ממשתנה סביבה, אף פעם לא מודפס):
vercel ls job-hunt --prod | head -5
curl -s -o /dev/null -w "%{http_code}\n" https://job-hunt-nine-orcin.vercel.app/dashboard
```

**טעויות נפוצות**

- למזג כמה PRs תלויים בבת אחת, ואז לא לדעת איזה מהם שבר.
- "CI ירוק אז סיימתי", בלי לפתוח את האתר.
- לנטרל בדיקה שנכשלת כדי "לשחרר את החסימה".

**הגדרת "סיום":** ה-PR מוזג עם CI ירוק, ה-deploy ב-`READY`, והקריטריונים העיקריים נבדקו באתר החי.

## שלב 9: שדרוגים אחד-אחד

**למה זה חשוב:** שדרוג של כמה ספריות יחד הופך כל תקלה לחידה: מי מהן שברה? שדרוג major יכול לשנות API,
ברירות מחדל או התנהגות בלי שגיאת קומפילציה. ספרייה אחת בכל PR, אחרי קריאת מדריך המעבר, שומרת על
שליטה.

- [ ] להתחיל מתמונת מצב: `npm audit` ו-`npm outdated`. לרשום מה חמור, ומה בכלל מגיע למשתמשי האתר
      (תלות של runtime) ומה רק לכלי פיתוח.
- [ ] לתעדף לפי חומרה וחשיפה: חולשה קריטית שמשתמש באתר יכול להגיע אליה קודם לכל השאר.
- [ ] **ספרייה אחת בכל PR** (`chore(deps): upgrade X a → b`).
- [ ] לקרוא את ה-changelog ואת מדריך המעבר, ולחפש בקוד את ה-APIs שהשתנו.
- [ ] קודם לנסות שדרוג minor או patch, או `overrides` לתלות עקיפה. רק אחר כך major.
- [ ] להריץ את כל הבדיקות, build, ובדיקה ידנית של האזורים שמשתמשים בספרייה (למשל המפה אחרי שדרוג `maplibre-gl`).
- [ ] אם השדרוג מסוכן (הרבה קבצים, שינוי framework, אין גרסה מתוקנת): **לעצור**, לתעד למה, ולהחליט
      עם בעל המוצר. לא "לדחוף בכוח".
- [ ] אין שדרוג major שנכפה בלי אישור.

```bash
npm audit --omit=dev            # מה מגיע ל-production
npm audit                       # הכל, כולל כלי פיתוח
npm outdated
npm install maplibre-gl@^6.16.0 # ספרייה אחת
npm ls tinypool                 # מאיפה מגיעה תלות עקיפה
npm test && npm run build
```

**טעויות נפוצות**

- `npm audit fix --force`, שמשדרג major בשקט ושובר דברים.
- לשדרג ספרייה רק כי יצאה גרסה חדשה, בלי סיבה (אבטחה, באג, פיצ'ר שצריך).

**הגדרת "סיום":** כל שדרוג נמצא ב-PR משלו, נקרא מדריך המעבר, הבדיקות וה-build עוברים, האזור שמושפע נבדק ידנית, ומה שלא שודרג מתועד עם הסיבה.
